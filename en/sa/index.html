01 / START

Receiving an analysis task

Start not with a solution, but with context: what problem we solve, who receives value, what constraints are already known, and how success will be measured.

  1. Capture the business goal.Understand the problem, expected effect and success criteria.
  2. Gather context.Documentation, interviews, current process, constraints.
  3. Model scenarios.Happy path, alternatives, errors and exceptions.
  4. Design system behavior.Data, integrations, roles, rules and NFRs.
  5. Align requirements.Development, QA, business and owners of adjacent systems.
  6. Support implementation.Change analysis, team answers, acceptance and updates.
Working question

“What will change for the business or user if we implement this task?”

High valueLow effortdo first
High valueHigh effortplan and decompose
Low valueLow efforttake if capacity allows
Low valueHigh effortreconsider necessity

03 / REQUIREMENTS

Requirement types

Different requirement levels answer different questions. Mixing them makes discussion, estimation and testing harder.

BusinessWhy the change is needed and what outcome is expected.
UserWhat users need to accomplish in their context.
FunctionalWhat the system must do: behavior, rules, calculations, states.
Non-functionalHow well it must work: performance, availability, security, usability.
Interface / IntegrationHow systems and users interact: UI, API, events, formats.
Data / TransitionData structure/quality and migration, cutover, coexistence needs.

04 / CHANGE

Requirement lifecycle & change management

Draft→Review→Approved→Implemented→Verified
  • Baseline — fix the agreed scope version;
  • Change request — separate a change from a clarification;
  • Impact analysis — assess UI, API, data, processes, tests, timelines and migrations;
  • Decision — record author, date, reason and chosen option;
  • Communication — update related artifacts and stakeholders.

05 / TRACE

Requirement traceability

A minimal chain helps you understand why a requirement exists and how its implementation will be confirmed.

Business goal→Requirement→Scenario→Acceptance→Test / Release
Check

A requirement without a goal is a candidate for removal. A requirement without a verification criterion is a source of disputes at acceptance.

06 / NFR

NFR catalog: what must not be missed

Performance

p95/p99 latency, throughput, payload

Availability

SLA/SLO, degradation, maintenance windows

Scalability

load growth, horizontal scaling

Reliability

retry, idempotency, recovery

Security

auth, access, audit, secrets

Data

retention, RPO/RTO, backup, deletion

Observability

logs, metrics, traces, alerts

Accessibility

keyboard, contrast, assistive tech

Measurability

“The system must work fast” is not an NFR. “p95 response for GET /orders ≤ 400 ms at 300 RPS” is a verifiable requirement.

10 / DISCOVERY

Discovery, Impact Mapping & Story Mapping

Before fixing a solution, it is useful to separate the problem, the expected effect and the specific implementation. This reduces the risk of thoroughly describing an unnecessary feature.

Problem statementwho experiences the problem, where and why it matters
Outcomewhat change in behavior or metrics is expected
Impact MapGoal → Actors → Impacts → Deliverables
Story Mapend-to-end user journey and release slices
Practice

If the discussion immediately starts with “let’s build a button / queue / microservice”, return to the goal, actor, current scenario and measurable result.

11 / SCENARIO

Use Cases

A Use Case is useful when the interaction sequence and system behavior variants matter.

ActorWho initiates the scenario
PreconditionsWhat must be true before start
Main flowSuccessful sequence of steps
AlternativesErrors and variants
PostconditionsSystem state after completion
Mini example

User places an order → system validates the cart → reserves stock → creates the order → starts payment. If stock changed, the system returns a conflict and suggests updating the cart.

User Stories

As a [role], I want [capability], so that [value].

INVEST: Independent · Negotiable · Valuable · Estimable · Small · Testable.

Given the user is authenticated
When they confirm the order

13 / ACCEPT

Acceptance Criteria and BDD

Acceptance criteria describe observable system behavior, not the implementation approach.

Scenario: successful payment
Given the order is in awaiting_payment status
And the payment method is available
When the user confirms payment
Then the payment is created once
And the order moves to paid
And an OrderPaid event is published
  • positive scenario;
  • alternatives and errors;
  • data boundaries;
  • repeated request / idempotency;
  • access rights;
  • observable result and side effects.

For an analyst, an API is a formalized contract between a data consumer and a provider.

200 OK
{
  "id": 123,

}

Responsestatus, headers, schema
Errorscodes, message, details, retryability
Rulesauth, idempotency, limits, versioning

Schemas

Idempotency

20 / ACCESS

Authentication, Authorization, OAuth/OIDC

Authentication

Confirms who performs the action: session, token, MFA, federation.

  • OIDC — identity layer on top of OAuth 2.0;
  • access token — access to the API;
  • refresh token — access renewal;
  • JWT — a token format, not an authorization protocol.

Authorization

Defines what is allowed.

  • RBAC — access through roles;
  • ABAC — rules by attributes;
  • Scopes — token permission boundaries;
  • resource ownership — access to specific objects.

26 / RELIABILITY

Reliability patterns

Timeout

limits waiting for a dependency

Retry + backoff

retries only transient errors

Idempotency

a retry does not create a double effect

Circuit breaker

stops an avalanche of calls

Outbox

aligns data write and event publication

Saga

coordinates a distributed business transaction

DLQ

isolates unprocessable messages

Reconciliation

finds and fixes discrepancies after the fact

27 / CHANNELS

Webhooks, polling & file exchange

  • Webhook: signature/HMAC, timestamp, retry policy, idempotency, 2xx response;
  • Polling: interval, cursor/watermark, rate limit, delta updates;
  • File/SFTP: naming, encoding, schema, delimiter, checksum, atomic upload, archive;
  • Batch: cut-off time, partial failure, reprocessing, reconciliation report.

28 / SERVICES

Microservice architecture

Benefits

  • independent scaling;
  • isolated releases;
  • explicit responsibility boundaries;
  • technology autonomy.

Challenges

  • network failures and latency;
  • distributed transactions;
  • observability and tracing;
  • contract compatibility.
Not a goal in itself

For a small product, a modular monolith is often simpler and cheaper to operate.

34 / FLOW

Kanban vs Scrum

Scrum

  • fixed sprints;
  • sprint goal and backlog;
  • roles and regular events;
  • changes are controlled within the iteration.

Kanban

37 / OBSERVE

Observability: logs, metrics, traces

Logs

what happened; structured fields, severity, context.

Metrics

how much and how fast; rate, errors, duration, saturation.

Traces

where time is spent in a distributed request.

  • correlation/request ID passes through the entire landscape;
  • PII and secrets do not get into logs;
  • there are business outcome metrics, not only CPU/RAM;
  • an alert is tied to an action, not just to a chart.

43 / ANTI-PATTERNS

Common analyst mistakes

  1. Jumping straight to a solutionFormulate the problem and value first.
  2. Ignoring NFRsPerformance, security and observability must be part of requirements.
  3. Describing only the happy pathAdd errors, retries, timeouts and edge cases.
  4. Losing traceabilityLink goal → scenario → requirement → test.
  5. Changing requirements silentlyA change must have an author, reason, impact and history.

52 / TOOL

Requirement Quality Checker

Review a requirement for ambiguity, measurability, atomicity, explicit obligation and testability. Prefer concrete thresholds (latency, volume, error rate), actor/subject and observable outcome.

  • Avoid vague words without criteria (fast, convenient, user-friendly);
  • State who/what the subject is and under which conditions behavior applies;
  • Make success measurable and verifiable in acceptance/testing.

Interactive checking is available in the Workbench tools.

53 / TOOL

Acceptance Criteria Builder

Capture expected behavior as scenarios: Given (context/preconditions), When (action/event), Then (observable result). This reduces ambiguity and links requirements to tests.

Scenario: Successful payment\nGiven the order is awaiting payment\nWhen the user confirms payment\nThen the order moves to status paid

Interactive scenario builder is available in the Workbench.

54 / TOOL

SLA / Availability Calculator

Translate availability targets into downtime budget for a period (e.g. 30/365 days). Use this to align NFRs, incident response and expectations with stakeholders.

  • 99.9% over 30 days ≈ ~43 min 49 s downtime;
  • 99.99% over 30 days ≈ ~4 min 23 s downtime;
  • Define measurement scope: whole service, endpoint, region, maintenance windows.

Interactive calculator is available in the Workbench.

55 / TOOL

Three-point / PERT Calculator

Use optimistic (O), most likely (M) and pessimistic (P) estimates to get expected effort (O + 4M + P) / 6 and uncertainty σ = (P − O) / 6. Helpful when uncertainty is significant and single-point estimates are risky.

Interactive PERT calculator is available in the Workbench.

60 / REQUEST

API tester

Run browser requests to inspect status, headers/body behavior and CORS constraints. The target API must allow CORS; do not enter secret tokens or sensitive data into shared tools.

  • Check method, URL, auth requirements and content type;
  • Inspect 2xx/4xx/5xx responses and error payloads;
  • Remember browser CORS differs from server-to-server calls.

Interactive API tester is available in the Workbench.

63 / GLOSSARY

Glossary

Artifact
A work product of analysis: document, model, diagram, or contract.
Stakeholder
A party that influences a decision or is affected by it.
Use Case
A scenario of interaction between an actor and the system.
User Story
A short description of value from a role perspective.
BPMN
Business Process Model and Notation for process modeling.
REST
An architectural style for network APIs.
DDD
Domain-Driven Design: modeling around the domain and its language.
CI/CD
Automation of integration, checks, and delivery of changes.
ACID
Transaction properties: atomicity, consistency, isolation, durability.
ADR
Architecture Decision Record — concise capture of context, decision, and consequences.
API Contract
A formal agreement on requests, responses, errors, and interaction constraints.
Backoff
Increasing delay between retry attempts.
Bounded Context
A boundary within which a domain model and language have unambiguous meaning.
CDC
Change Data Capture — streaming changes from a data source.
Circuit Breaker
A pattern to temporarily stop calls to an unstable dependency.
Correlation ID
An identifier for tracing one business request across multiple systems.
DLQ
Dead Letter Queue — a queue for messages that could not be processed correctly.
Eventual Consistency
A model that allows temporary divergence of state between components.
Idempotency
A property where repeating an operation does not create additional business effect.
NFR
Non-functional requirement: performance, availability, security, and other quality attributes.
Outbox
A pattern for reliably publishing events together with a data change transaction.
RPO
Recovery Point Objective — acceptable data loss expressed in time.
RTO
Recovery Time Objective — acceptable service recovery time.
Saga
A pattern for coordinating a distributed business transaction via steps and compensations.
SLA
Service Level Agreement — contractual service level.
SLO
Service Level Objective — target service quality measure.
Traceability
Linking a requirement to goals, scenarios, implementation, and verification.
Webhook
An HTTP callback sent by a source when an event occurs.
